# 需求共识确认

## 目标

在开始实质工作之前，用尽量少的问题，把模糊需求变成双方认可的执行共识。

## 何时启用

- 用户提出新需求、布置任务、请求修改：写代码、改配置、做调研、写文档、跑命令、设计方案等。
- 不启用：纯知识问答或闲聊；用户明确要求“直接做/不用确认”；继续执行已经确认过的同一任务；维护本 skill 自身。

## 硬性规则

1. **先确认，后执行。** 共识达成前只做只读探查（读文件、检索、查文档），不做写入、删除、部署、发送等实质操作。
2. **每轮 1–3 个问题**，用 `AskUserQuestion` 工具提出，不要用普通文本提问。
3. **每题只做一个决定**；提供 2–4 个互斥选项；推荐项放第一位并标注“（推荐）”。
4. **只问会改变你行动的问题。** 能从环境里查到的事实自己查，不要问用户。
5. 用户用中文就用中文提问；用户换语言就跟着换。
6. 提问由当前主 agent 直接完成。不要派生后台 subagent 代问——subagent 无法与用户实时来回，构不成共识。

## 流程

### 第 1 步：复述

用 1–2 句话复述你理解的目标（这是陈述，不是提问），让用户能立刻纠正偏差。

### 第 2 步：找出关键未知

从下面的维度里，挑出当前最影响执行的 1–3 个：

- **目标与成功标准**：什么算完成？
- **范围边界**：哪些做、哪些不做？
- **交付物**：形式、位置、语言、格式。
- **约束**：技术栈、兼容性、时间、风格、依赖。
- **风险**：是否涉及不可逆操作、敏感数据、外部发布。
- **验证方式**：如何验收或测试。

已经清楚的维度不要问。优先问“答错会导致返工”的问题。

### 第 3 步：第一轮提问

一次 `AskUserQuestion` 调用提出 1–3 个问题，每题给出你的推荐。

### 第 4 步：循环

根据回答更新理解，重新找出还有哪些会改变执行的关键未知。若仍有，进入下一轮（仍是 1–3 题）。

- 通常 1–2 轮足够，复杂任务不超过 3 轮。
- 超过 3 轮仍有分歧：停止追问，列出 2–3 个可选方案（含“按推荐假设执行”），让用户选一个。

### 第 5 步：共识摘要与最终确认

动手前，用不超过 8 行给出：

- 目标
- 范围（做 / 不做）
- 交付物
- 关键约束
- 验收标准
- 主要假设

然后用 `AskUserQuestion` 问最后一个确认题：

- 以上理解准确，开始执行（推荐）
- 需要修正（请说明）
- 先不执行

### 第 6 步：执行与变更

确认后立即执行。执行中发现与共识冲突的新信息，暂停并重新确认，不要自行扩大范围。

## 提问密度

- 高风险、不可逆、多文件改动：2–3 题。
- 一般任务：1–2 题。
- 极简且目标明确：1 题确认即可（例如“确认按 X 方式处理？”）。
- 若用户连续两轮全选推荐：后续轮次只问高风险项。

## 反模式

- 复述完就直接开工。
- 一轮问 4 题，或把多个决定塞进一题。
- 问“要不要我做得更好”这类不改变行动的假问题。
- 问用户本可以自己查到的事实（路径、现有实现、依赖版本）。
- 只给一个选项，或开放式提问（应给互斥选项 + 推荐）。
- 把确认拖成审讯：超过 3 轮还在追问。

## 示例

用户：“帮我给这个项目加个登录功能。”

**第 1 轮**（一次 `AskUserQuestion`，3 题）：

1. 认证方式：邮箱+密码（推荐）/ 第三方 OAuth / 两者都要
2. 用户数据：复用现有数据库（推荐）/ 新建用户表 / 外部认证服务
3. 范围：仅登录（推荐）/ 登录+注册 / 登录+注册+找回密码

**第 2 轮**（视回答而定，1–2 题）：会话方案、是否需要前端页面、是否补测试。

给出共识摘要并确认后，再开始实现。

## 与其他 skill 的关系

- 需要深度压力测试方案时，可参考 `grilling`；但本 skill 以“达成执行共识”为目标，每轮上限 3 题。
