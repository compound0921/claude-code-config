# Release 说明规范

来源：ShareScreen 的 Release 页面（`github.com/compound0921/ShareScreen/releases`）。以 v1.3 之后的现行格式为准。

## 结构

1. **固定开篇**：一句话说明项目是什么、给谁用。
2. **版本主题**：一段说明这一版解决了什么、为什么值得更新，2–4 句。
3. **小节**按序排列，没有内容就省略：
   - `### 新增`
   - `### 变更`
   - `### 修复`
   - `### 说明`
4. 每条用「**加粗的一句话结论。** 具体行为、边界、代价」的写法。
5. 补丁版本（如 v1.7.1）可以不写小节，用一段修复说明加一段发布包说明。

## 每节写什么

- **新增**：用户能感知的新能力。写清怎么触发、适用范围、限制。
- **变更**：旧行为 → 新行为、默认值变化、对已有配置和用户的影响。
- **修复**：症状 → 根因（一两句）→ 现在的结果。不写用户感知不到的内部重构。
- **说明**：取舍、安全提醒、已知限制、可能的误判。主动写出代价，不藏。

单个重要限制可以单独开小节，例如 `### 关于 WGC 的黄色采集边框`。

## 语言与格式

- 中文，面向使用者，不用 commit 术语、内部类名和缩写。
- 关键结论加粗；代码、字段、默认值、错误信息用反引号。
- 段落约 40–50 字换行，与现有 Release 一致。
- 不用营销形容词（“强大”“极致”“革命性”），不写感谢名单和 commit 列表。
- 数字写实测值：体积、延迟、帧率、端口号。
- 不写「下载哪个」、附件文件名或安装包说明；Release 页面已列出附件。
- 安全相关内容必须单列在「说明」：明文传输、默认密码、默认监听 `0.0.0.0`、额外开放的端口。
- 版本号与标签用 `vX.Y.Z`；标题默认与标签一致，需要时写成 `项目名 vX.Y.Z`。

## 首次发布 / 大版本

首次发布也沿用现行结构，可补充「要求」「能做什么」「已知限制」等说明。

**不写「下载哪个」或附件清单**——Release 页面本身会列出附件。

## 模板

```markdown
<项目一句话介绍。>

这一版<主题：改了什么、为什么>。

### 新增

- **<结论>。** <行为、适用条件、限制>

### 变更

- **<结论>。** <旧行为 → 新行为；对已有用户的影响>

### 修复

- **<症状>。** <根因简述>；现在<结果>。

### 说明

- **<取舍或限制>。** <后果与建议>
```

补丁版本：

```markdown
修复：<症状与原因>。<触发条件与影响范围>。

<发布包有变化时补一句包含内容。>
```

## 写法示例

结论先行，再补原因：

> **接了 HDMI 显示器之后，观众只有画面、没有声音。** 程序原先只抓系统默认播放设备的回环，而默认设备不一定是有声的那台。现在可以指定采集设备；设备不在时退回默认设备并说明。

变更要写清默认值和新旧差异：

> **远控端口现在默认就监听。** 这一版之前，不开远控就一个端口都不多占。现在为了接收「请求开启」，这个端口默认一直开着；不想要就取消勾选那一项。

说明要给出代价，不只给结论：

> **请求通道和观看链路一样是明文的。** 不要在不可信的网络里开着它。

## 检查清单

- [ ] 固定开篇和版本主题段齐全
- [ ] 小节顺序正确，没有内容的小节已删除
- [ ] 每条都有加粗结论
- [ ] 变更写明了默认值和旧行为
- [ ] 修复写明了症状、根因和触发条件
- [ ] 安全与限制写进了「说明」
- [ ] 没有 commit 列表、内部术语和营销词
- [ ] 版本号、标签、标题一致
- [ ] 草稿经用户确认后才发布
