# 版本号规划

适用于按 SemVer 发布的桌面端、服务端和工具类项目。以 ShareScreen 的 `0.1.0 → 1.0 → 1.7.1` 发布记录为参照。

## 位数定义

| 位 | 何时 +1 | 示例 |
|---|---|---|
| **MAJOR** | 用户必须改配置或换用法才能继续用：配置格式不兼容、链接/协议变化、最低系统要求提高、删除已有能力 | 放弃 Win10 支持、配置字段改名 |
| **MINOR** | 新增功能，或用户可感知的默认行为变化 | UPnP 自动映射、远程控制、默认采集源变化 |
| **PATCH** | 只修 bug，不新增功能、不改默认值 | 音频静音修复 |

`0.x` 阶段不承诺兼容；达到“敢直接推荐给别人用”时发 `1.0.0`。

## 发版前反推版本号

看这份 Release 说明里有哪些小节：

- 有「新增」→ 至少 MINOR。
- 有「变更」（默认值、行为、端口、配置含义）→ MINOR。
- 只有「修复」→ PATCH。
- 出现“旧配置不能用 / 链接变了 / 系统要求变高” → MAJOR。

**硬规则：PATCH 不得包含新增功能或默认值变化。** 塞不进去就升 MINOR。

反例：v1.3.1 新增了“采集哪台设备的声音”，还把默认采集源从 GPU 改成“屏幕（推荐）”，却发成了 PATCH。这会让用户不敢无脑升级补丁版。

## 节奏

- **一个 MINOR 对应一个主题**，主题就是 Release 说明里“这一版……”那一段；主题说不清就该拆版。
- 功能在 `develop` 上攒，稳定后一次发布；不为每个合并或 PR 发版。
- 纯重构、内部整理、无用户感知的改动不发版。
- 补丁版本只解决需要立即修复的用户可见问题。

## 分支与发布

| 类型 | 流程 |
|---|---|
| MINOR / MAJOR | `develop` 合入 `main` → 打 `vX.Y.Z` |
| PATCH 热修 | 从 `main` 切 `fix/<slug>` → 修复 → 合回 `main` → 打 `vX.Y.Z` → 再回合 `develop` |
| 预发布 | 从 `develop` 切分支，打 `vX.Y.Z-beta.N`，不合并 `main` |

热修不能动 `develop` 上正在攒的功能；回合 `develop` 时解决冲突，不要把 `main` 上的临时改动覆盖回去。

## 标签与标题

- 标签统一 `vX.Y.Z`，带注释：`git tag -a v1.8.0 -m "v1.8.0"`。
- Release 标题与标签一致；需要时写成 `项目名 vX.Y.Z`。
- 版本号一经发布不再复用；撤回后重新发布要递增。

## 常见反模式

- 补丁版里夹新功能或默认值变化。
- 每个 PR 都发一版，版本号变成流水账。
- 长期停在 `0.x` 却对外推荐使用。
- 改了默认值却不升 MINOR。
- 预发布标签混进 `main` 或正式发布列表。

## 规划示例

| 版本 | 内容 |
|---|---|
| `1.8.0` | 下一个功能主题 |
| `1.8.1` | 只修 1.8.0 暴露的 bug |
| `1.9.0` | 下一组功能 |
| `2.0.0` | 配置不兼容、协议改动或放弃旧系统时 |
