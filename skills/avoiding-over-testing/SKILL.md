# 不要过度测试

## 目标

用最少的测试拿到足够的回归保障，把时间留给功能本身。

## 何时启用

- 写新功能、改代码、修 bug 时，决定要不要补测试、补多少。
- 跑测试、改测试、判断“测够了没有”时。
- 用户明确说“别过度测试”“少写点测试”。

不启用：用户明确要求补测试、提高覆盖率或完整回归时，以用户要求为准。

## 规则

1. **测试跟着行为走。** 一个行为一个测试，测关键路径和真实可能回归的点；不为每个分支、每行代码写测试。
2. **低风险改动不新增测试。** 文案、注释、配置、样式、版本号、一行机械修复。已有测试覆盖时不再重复写。
3. **不追覆盖率数字。** 覆盖率是结果，不是目标；不为凑数字写无断言或重复的测试。
4. **只跑受影响的测试。** 改动后跑相关文件或模块的测试，通过即停；全量套件留给提交前、发布前或用户要求时。
5. **验证一次即够。** 同一事实不重复读文件、不重复跑命令、不换工具再确认一遍。只有出现新信息时才重新验证。
6. **优先复用。** 已有测试或现有手动验证路径能覆盖的，不新建测试文件或测试框架。
7. **让位用户。** 用户要求补测试、覆盖率或完整回归时，按用户要求执行，本 skill 不适用。

## 自检

写测试或再跑一次之前，逐条问：

- 这个测试能抓住真实可能的回归吗？
- 已有测试是否已经覆盖？
- 改动风险是否低到不需要测试？
- 我是不是在重复验证同一个结论？
- 我跑的是受影响的测试，还是全量？

答案指向多余动作，就停下。

## 反模式

- 改一行文案，顺手补一个测试文件。
- 为每个边界、每个分支、每个异常都写用例。
- 修完 bug 后反复跑全量测试确认“真的修好了”。
- 已经读到答案，又换命令或换文件再查一遍。
- 用户没要求，却为了覆盖率补一堆无意义用例。

## 示例

**改文案**
> 不新增测试；仓库若有文案/快照测试，只跑相关那一个。

**修 bug**
> 加一个能复现该 bug 的回归测试，跑该测试文件；通过即停。

**改函数逻辑**
> 已有测试覆盖该函数：更新受影响用例，跑该文件；不全量重跑。

**低风险配置**
> 不写测试，按需手动验证一次。

## 与其他 skill 的关系

- 是否需要测试、测到什么程度，先按 `confirming-requirements` 与用户达成共识。
- 本 skill 只约束“别多做”，不降低用户明确要求的测试标准。
